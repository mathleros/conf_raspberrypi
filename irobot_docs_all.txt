# Structure du package `irobot`

Cette organisation vise à rendre visible la hiérarchie fonctionnelle du robot :

```text
src/irobot/
├── common/        # noyau : config, domain (skills, orchestrator), hardware, interfaces
├── app/           # application vocale `robot` : LLM + intents + missions
└── tools/         # outillage développeur : dépend de common, jamais importé
    ├── calibrate_distance.py
    ├── vision_diagnostic.py
    └── robot_test/    # `robot-test` : banc de test du noyau (sans LLM ni intents)
```

## Configuration

La calibration du runtime est chargée depuis
[config/runtime_settings.toml](config/runtime_settings.toml). Les sections,
clés et types TOML sont vérifiés au chargement ; une clé inconnue ou une valeur
mal typée déclenche une erreur explicite. Les paramètres du client LLM sont
séparés dans `config/llm_settings.py` et proviennent des variables `LLM_*`.
Les imports historiques depuis `config/settings.py` restent compatibles.

## Règle de conception

- `skills/primitives` : actions atomiques du robot
- `skills/perception` : lecture de capteurs et perception visuelle
- `skills/behaviors` : comportements / tâches composites
- `orchestrator` : planification, exécution et supervision

Le LLM produit une intention de haut niveau ; l'orchestrateur la transforme en
plan de skills primitives, qui pilotent le robot via `RobotController`.
Le LLM n'est jamais un pilote matériel.

## Points d'entrée

- `robot` (`app/app.py`) : application vocale, LLM + intents
- `robot-test` (`tools/robot_test`) : banc de test du noyau (`--behavior`, `--text`, `--audio`, mot d'activation)
- `calibrate-distance` et `vision-detect-live` : outils (`tools/`)
- Dépendances : `common` ne dépend de rien ; `app` et `tools` dépendent de `common`, jamais l'un de l'autre.

## Organisation du runtime texte et vocal

Le point d'entrée `robot` est [app/app.py](app/app.py) : il assemble le matériel
(`build_hardware_runtime`) puis le `VoiceRuntime` de
[interfaces/voice_runtime.py](interfaces/voice_runtime.py), et ferme toujours le matériel
(`close_hardware_runtime`) dans son `finally`.
`VoiceRuntime` gère le micro, les transcriptions et les arrêts vocaux immédiats.
En écoute continue, les commandes exigent le mot d'activation `--wake-word` (défaut « robot » ; chaîne vide pour le désactiver) ; « stop » fonctionne sans lui, et `--text` comme `--once` ne l'exigent pas.
Le texte direct et les transcriptions passent ensuite par
[interfaces/command_service.py](interfaces/command_service.py), qui choisit le
parseur, prépare et valide les intents, puis soumet le plan à
[MissionOrchestrator](domain/orchestrator/mission_orchestrator.py).

| Module | Responsabilité |
| --- | --- |
| `interfaces/command_service.py` | Point d'entrée texte, assemblage des services, choix du parseur, traces JSONL et arrêt matériel final |
| `interfaces/voice_constants.py` | Vocabulaire et valeurs par défaut des plans |
| `interfaces/voice_llm_transport.py` | Prompts, HTTP, formats de réponse, métriques et cache |
| `interfaces/intent/llm_intent_parser.py` | `ask_llm_for_intent_plan_with_trace`, grounding, repli local et préchauffage |
| `interfaces/intent/text_intent_parser.py` | Parsing déterministe du texte en liste d'intents |
| `interfaces/intent/intent_parser.py` | Contrat commun des parseurs |
| `interfaces/intent/plan_validator.py` | Normalisation des noms/cibles, validation et bornage des paramètres |
| `interfaces/language_controller.py` | Exécution des étapes compilées avec perception et contrôle d'obstacle |
| `domain/intent.py` | Modèle métier `Intent`, indépendant des interfaces |
| `domain/intent_validator.py` | Autorisation des intents et contrôle des cibles structurées normalisées, sans analyse du texte |
| `domain/perception.py` | Cibles sémantiques de perception (`PerceptionTarget`) |
| `domain/orchestrator/planner.py` | Décomposition des commandes composées et plan typé intent → skills |
| `domain/orchestrator/mission_orchestrator.py` | Séquence, retries, délais et transitions de mission ; exécuteur et contrôle d'arrêt injectés |
| `domain/orchestrator/mission_state_machine.py` | État courant de mission et métadonnées |
| `hardware/audio/voice_input.py` | Capture ALSA, nettoyage du processus et transcription Vosk |
| `hardware/runtime_factory.py` | Assemblage moteur/capteur/caméra sur Raspberry Pi |

Le LLM (`ask_llm_for_intent_plan_with_trace`) et `TextIntentParser` produisent tous deux une liste d'`Intent`.
`SkillPlanner` développe les commandes composées et produit des `SkillPlanStep`
qui associent chaque intent exécutable à ses skills. `LanguageController` reçoit
ces étapes et les exécute ; il ne parse pas de texte et ne choisit pas les skills
du plan vocal. Toute commande texte suit le même parcours dans `CommandService`.

`CommandService` utilise la composition, sans mixins ni état vocal partagé.
Le domaine n'importe ni `interfaces` ni `hardware`. L'orchestrateur reçoit les
étapes, une fonction d'exécution, un contrôle d'arrêt et un observateur optionnel ;
il ne connaît ni le micro, ni le LLM, ni les fichiers JSONL, ni les pilotes.
Les délais sont mesurés avec une horloge monotone injectable. Ils sont vérifiés
au retour d'une étape et entre étapes, sans interruption forcée d'un appel
bloquant ; les skills et le contrôleur restent responsables de l'arrêt immédiat.
Les anciens chemins et mixins supprimés ne sont pas réexportés pour compatibilité.
Les adaptateurs matériels sont importés uniquement lors de leur utilisation :
charger le runtime ou traiter du texte n'initialise ni ALSA, ni Vosk, ni GPIO, ni caméra.

La perception caméra attend une image traitée pour la cible demandée au démarrage
et lors d'un changement de cible (par exemple balle rouge vers marqueur avec
« suis-moi »). Une image encore en traitement pour l'ancienne cible ne satisfait
pas cette attente, limitée à une seconde et interrompue à la fermeture ou en cas
d'échec caméra. Un dépassement est journalisé et ne fournit aucune détection.
Une détection déjà fournie pour la même image est renvoyée avec `cached=True`,
comme un visage mémorisé pendant le délai de grâce. Le suivi et l'approche ne
pilotent pas les moteurs sur ces observations : une nouvelle image est nécessaire
avant de répéter une correction. Cela évite les rotations répétées sur une
position ancienne lorsque le traitement caméra est plus lent que la boucle moteur.
Les intentions `follow_person`, `follow_red_ball` et `follow_object` utilisent
le même suivi continu, sans limite de tentatives, de tracking ou de recherche
lorsqu'aucune durée n'est demandée. À distance de consigne, le robot attend puis
reprend si la cible s'éloigne. Lors d'une perte de cible, il arrête la translation,
attend le délai de perte courte puis recherche en rotation jusqu'à réacquisition
ou arrêt. Cela vaut aussi pour le marqueur ArUco.
Une durée explicitement demandée (`duration_s`) conserve le mode temporisé et
ses bornes. `search_and_approach_object` reste une approche ponctuelle bornée,
y compris « approche-toi de moi » avec ou sans LLM.
`follow_person` et `search_and_approach_object` acceptent un paramètre `person` : le prénom de la galerie (casse libre) ; un prénom inconnu est refusé avec « personne inconnue ».
Les arrêts vocaux, les obstacles, la validation et les erreurs matérielles restent
prioritaires ; une erreur de suivi n'est pas relancée automatiquement.
Les traces `step_result` incluent le statut, le message et les données des skills.
Le runtime n'intègre pas d'adaptateur P5 qualifié ; toute protection matérielle
doit fonctionner indépendamment du logiciel.

La distance ArUco du runtime et du diagnostic utilise la même fonction
[estimate_marker_distance_cm](hardware/camera/detector/aruco_detector.py) : pose
`solvePnP` à partir des quatre coins, puis distance directe objectif–centre
du marqueur. L'inclinaison et le décentrage sont pris en compte. Le carré est
supposé mesurer 8 cm ; la focale provisoire est 600 px pour l'image tournée
480×640, avec centre optique centré et distorsion nulle. Sans calibration
optique, la précision réelle, notamment aux bords, reste à vérifier sur le Pi.
Une pose inexploitable est journalisée et ne fournit aucune détection, sans
repli sur la largeur apparente. L'estimation des balles, les seuils de position
et l'absence de fusion ultrason pour les marqueurs restent inchangés.

## Correction du contre-jour

[frame_enhancer.py](hardware/camera/frame_enhancer.py) partage la correction entre
le runtime, `vision-detect-live` (y compris son mode aperçu) et
`calibrate-distance`. Les images restent en RGB jusqu'à la conversion propre
au détecteur ou à l'affichage. Le CLAHE est créé une seule fois par flux et
appliqué uniquement au canal de luminosité L de LAB, avant toute détection.

Dans [runtime_settings.toml](config/runtime_settings.toml), section
`[camera]`, la correction est activée avec `exposure_value = 1.0` EV,
`clahe_enabled = true`, `clahe_clip_limit = 3.0` et une grille fixe 8×8.
La compensation d'exposition est transmise à Picamera2 après configuration et
avant démarrage ; elle dépend de l'exposition automatique de la caméra.
Si `ExposureValue` n'est pas disponible, un avertissement est journalisé et le
CLAHE reste utilisable. Une erreur de réglage n'est pas masquée.

Pour retrouver le comportement précédent, régler `exposure_value = 0.0` et
`clahe_enabled = false`. Ces valeurs sont aussi les défauts lorsque les clés
sont absentes. Un booléen CLAHE invalide, une limite non positive ou une
exposition non finie/hors de [-8, 8] EV est refusé explicitement.

Le traitement améliore le contraste local mais ne récupère pas les détails
déjà perdus par sous-exposition ou saturation. Une compensation positive peut
surexposer l'arrière-plan ; le CLAHE peut amplifier le bruit et modifier les
valeurs HSV malgré la conservation des canaux a/b. Vérifier sur le Pi les
balles rouge/jaune, les IDs ArUco, les faux positifs et la latence, en éclairage
normal et en contre-jour. Refaire la calibration de distance avec les mêmes
réglages que le runtime si la segmentation et les diamètres mesurés changent.

## Détection de visages

[face_detector.py](hardware/camera/detector/face_detector.py) utilise YuNet uniquement
pour les cibles explicites `face` et `human` (alias). Le runtime applique d'abord
le même CLAHE que pour les balles/ArUco, puis le wrapper convertit RGB vers BGR.
Le modèle est chargé à la première image demandée pour un visage, jamais pour
une balle ou un marqueur. Un modèle absent ou invalide et une erreur YuNet sont
signalés explicitement ; une erreur de capture arrête le flux sans détection.

Le modèle [face_detection_yunet_2023mar.onnx](../../assets/vision/face_detection_yunet_2023mar.onnx)
provient d'[OpenCV Zoo](https://github.com/opencv/opencv_zoo/tree/main/models/face_detection_yunet),
sous [licence MIT](../../assets/vision/face_detection_yunet_LICENSE.txt).
Taille : 232 589 octets ; SHA-256 :
`8f2383e4dd3cfbb4553ea8718107fc0423210dc964f9f4280604804ed2552fa4`.
Il est livré avec le projet, sans téléchargement automatique au démarrage.

La section `[camera]` de [runtime_settings.toml](config/runtime_settings.toml)
configure `face_model_path` (relatif au TOML ou absolu), `face_width_cm = 8.0`,
`face_score_threshold = 0.85` et `face_grace_frames = 10`.
La distance indicative vaut `focal_px × face_width_cm / largeur_du_visage_px`,
avec la focale caméra existante et les pixels de l'image orientée, sans fusion
ultrason. Largeur et seuil doivent être finis et positifs, le seuil au plus 1,
et la tolérance un entier non négatif.

Le visage de plus grande largeur admissible est sélectionné ; sa sortie est
un `ObjectDetection(label="face")` avec position, distance, confiance et largeur
dans `diameter_px`. La mémoire conserve la dernière observation jusqu'à N images
traitées sans visage, puis retourne `None`. Elle est effacée lors d'un changement
de cible, de dimensions ou d'une erreur YuNet ; une réacquisition remet le compteur
à zéro. Les appels répétés à `detect()` ne consomment pas cette tolérance.
Pendant la grâce, position/distance/confiance sont celles de l'ancienne observation,
pas des mesures actuelles ; la durée réelle dépend du débit caméra. Régler
`face_grace_frames = 0` pour que toute perte soit immédiatement visible au suivi.

Il s'agit de détection, pas de reconnaissance d'identité : plusieurs visages
peuvent provoquer un changement de personne suivie. La distance varie avec la
largeur réelle et l'orientation du visage et doit être vérifiée sur le Pi avant
suivi moteur. Aucune image ni donnée biométrique n'est enregistrée par le wrapper.
Les contrôleurs de suivi existants acceptent la source `face` sans nouveau contrat.
La commande vocale « suis-moi » et les formulations « moi », « humain », « personne »
et « visage » routent vers le détecteur de visage (`face`). Les formulations « marker »
et « tag » routent vers le marqueur ArUco, et « balle » vers les détecteurs de couleur.

## Diagnostic vision

`uv run vision-detect-live` lance [vision_diagnostic.py](tools/vision_diagnostic.py)
sur la caméra 0 OV5647, avec affichage X11 et rotation habituelle de 90°.
Il recherche simultanément l'ID ArUco `DICT_4X4_50 / 1`, le visage sélectionné
par YuNet et la meilleure balle de chacune des couleurs rouge et jaune.
Comme pour `robot-test`, la galerie configurée (par défaut `assets/face/`) est chargée
au démarrage : chaque photo `.jpg`, `.jpeg` ou `.png` doit contenir un seul
visage et son nom de fichier fournit le prénom. SFace compare le plus grand
visage admissible à toutes les photos avec le seuil configuré. Le diagnostic
affiche `IDENTITY: <prénom>`, `unknown` si aucun score n'atteint le seuil, ou
`no face` en l'absence de visage. L'identité correspond uniquement au visage
sélectionné, pas nécessairement à toutes les personnes visibles. Les accents
sont retirés dans l'aperçu OpenCV, mais conservés dans le terminal.
Si le modèle SFace ou la galerie est indisponible ou vide, un avertissement et
`IDENTITY: unavailable` le signalent ; la détection générique continue.
Le CLAHE n'est appliqué qu'une fois à chaque image avant les trois détecteurs.
Le visage et les balles ont des rectangles distincts ; le marqueur conserve
ses quatre coins et sa distance par pose. Les statuts et distances sont affichés
à l'écran et journalisés lors de changements. Les objets colorés non classés
comme balles ne sont pas présentés comme balles.

`uv run vision-detect-live --preview-only` affiche le même flux corrigé et tourné,
sans lancer les détecteurs, afficher de statut ni annoter l'image.

Un visage conservé pendant le délai de grâce est marqué `memorized`, avec sa
dernière boîte et ses anciennes mesures. Le diagnostic utilise les réglages
caméra du TOML, ne commande aucun moteur et n'enregistre aucune image.
Le modèle YuNet doit être disponible ; une erreur de détection n'est pas
assimilée à une absence. Appuyer sur `q` ou Ctrl+C pour quitter.
Pour le lancement Python direct, utiliser `python -m irobot.tools.vision_diagnostic`.

Dans `handle_transcript()`, toute occurrence du mot `stop`, `arrête`, `halte` ou
`pause` (accents, casse et ponctuation normalisés) entraîne immédiatement
`robot.stop()` puis la demande d'arrêt d'urgence, avant tout appel au parseur,
au LLM ou à la perception. Cela vaut aussi sans mission active et dans une
phrase contenant d'autres commandes. La mission est marquée `aborted` ;
le signal d'annulation interdit les retries et les étapes suivantes, même si
la planification LLM est encore en cours. Une nouvelle commande ne peut effacer
ce signal qu'une fois le worker précédent terminé.
L'entrée directe `handle_text_as_plan()` et l'écoute continue utilisent le même
chemin de planification ; la priorité lexicale des arrêts s'applique à
`handle_transcript()`.

## Organisation du contrôleur robot

[RobotController](interfaces/robot_controller.py) adapte le pilote injecté :
mouvements, vitesse, surveillance du capteur injecté et arrêt d'urgence logiciel.
Le pilote [SmartCar2WD](hardware/smart_car/smart_car.py) ne gère que les moteurs
et leurs GPIO ; le CLI est séparé dans [hardware/smart_car/cli.py](hardware/smart_car/cli.py).
Aucun mode protégé, permis de mission ou cycle P5 n'est conservé.

`RobotController` gère aussi les mouvements temporisés : horloge injectable,
durée finie et positive ou nulle, vérification d'arrêt, vérification d'obstacle
et arrêt final même en cas d'erreur.
La période de contrôle maximale est de 20 ms ; le recul ne vérifie pas
l'obstacle frontal. Une erreur ou une absence de mesure du capteur d'obstacle
est journalisée et traitée comme un obstacle.

`stop()` transmet directement le zéro au pilote, sans attendre de verrou,
de capteur ou de temporisateur. `request_emergency_stop()` positionne d'abord
le signal d'annulation puis appelle `stop()`. Les départs de mouvement sont
inhibés tant que le signal est actif. Une lecture matérielle ou LLM bloquée
peut retarder la fin du worker, mais ne bloque pas l'appel vocal à `stop()`.
La latence physique dépend toujours du pilote et du matériel : ces contrôles
logiciels ne remplacent pas une protection indépendante qualifiée.

Les tests [de structure du runtime](../../tests/unit/test_voice_runtime_structure.py)
et [du contrôleur](../../tests/unit/test_robot_controller_structure.py) vérifient
les limites 500 lignes/module et 50 lignes/fonction et les imports matériels paresseux.
Les [tests d'arrêt d'urgence](../../tests/unit/test_emergency_stop.py) couvrent
l'arrêt sans mission, les phrases composées, la planification et l'ultrason
bloqués, ainsi que l'annulation des mouvements et des étapes suivantes.

# Orchestration des skills du robot

Ce package regroupe la planification, l'exécution et le suivi des missions.

## Objectif

Le LLM ne doit pas piloter directement les GPIO. Sa fonction est plutôt :
- formuler l'intention,
- proposer un plan de haut niveau,
- transmettre une tâche structurée à l'orchestrateur,
- éviter les commandes non validées.

L'orchestrateur exécute un plan compilé, sans dépendance vers les interfaces
vocales, le LLM, les traces JSONL ou les pilotes matériels.

## Composants

### `SkillExecutor`

Exécute une `Skill` dans un `SkillContext` et renvoie un `SkillResult`.

### `SkillPlanner`
Décompose les intents composés en intents exécutables, puis compile chacun en
un `SkillPlanStep` qui associe l'intent à la séquence de skills enregistrées.
Le résultat est déterministe et ne laisse pas le LLM décider librement des actions.

### `MissionStateMachine`

Formalise les phases d'une mission :
- `idle`
- `planning`
- `executing`
- `success`
- `failed`
- `aborted`

### `MissionOrchestrator`

Possède la machine d'état et exécute les `SkillPlanStep` dans l'ordre :
retries, budgets par étape/mission et abandon à la première étape non terminée.
Un suivi continu n'a pas d'échéance et n'est pas relancé après erreur.
L'horloge monotone est injectable pour les tests.

Les dépendances d'exécution sont passées à `execute` : fonction d'exécution d'une
étape, contrôle d'arrêt et observateur facultatif d'événements.
`CommandService` adapte ces événements en JSONL et garantit l'arrêt matériel
dans un `finally`. Une exception d'exécution marque la mission en échec et se
propage ; un plan vide est une erreur explicite.

Les délais ne préemptent pas une skill bloquante : ils sont vérifiés après
l'appel et entre étapes. Les contrôles d'urgence des skills/du robot restent
indispensables.

## Exemple d'utilisation

Le service d'application injecte ici le contrôleur déjà assemblé :

```python
from irobot.app.domain.intent import Intent
from irobot.app.domain.orchestrator import MissionOrchestrator, SkillPlanner

planner = SkillPlanner()
steps = planner.plan_intents([Intent(name="stop")])
mission = MissionOrchestrator()
try:
    results, status = mission.execute(
        steps,
        controller.handle_planned_step,
        stop_requested=robot.emergency_stop_requested,
    )
finally:
    robot.stop()
```

# Configuration iRobot

Les paramètres du robot sont dans [runtime_settings.toml](runtime_settings.toml).
Ils sont chargés par `settings.py` au démarrage.

- `[runtime]` : vitesses et délais d’exécution, et nombre de manœuvres inverses après un alignement trop fort
  (`target_recovery_attempts`, 0 désactive) ; attente robot arrêté avant balayage après perte de cible
  (`target_loss_wait_seconds`, commune à `follow_object` et `approach_target`), stabilisation après un alignement
  (`align_settle_seconds`) et fenêtre de manœuvre inverse (`target_recovery_window_seconds`, ≥ `align_settle_seconds`).
  La durée d’une impulsion d’alignement est proportionnelle au décalage horizontal de la cible : `align_gain` en est
  la fraction appliquée, bornée entre `align_step_min_seconds` et `align_step_max_seconds` (max ≥ min).
- `[limits]` : bornes des déplacements, durées et plans.
- `[stand_off]` : distance de consigne par défaut (`default_cm`) et tolérance en % (`tolerance_percent`) communes au suivi
  et à l’approche ; une distance dite dans la phrase reste prioritaire.
- `[camera]` : dimensions de capture et d’image orientée, seuil de bord de suivi (`edge_offset_threshold`), focale pour les
  distances, correction d’image et détection de visages.
- `[human_follow]` : paramètres temporels du suivi humain.

Modifie les valeurs dans le TOML plutôt que les valeurs par défaut de `settings.py`.
Les clés absentes utilisent les valeurs par défaut ; une clé inconnue, une section
mal formée ou une valeur du mauvais type provoque une erreur au chargement.
`face_model_path` peut être absolu ou relatif à `runtime_settings.toml`.
Pour recalibrer la focale, lance `uv run calibrate-distance --known-distance-cm 100`,
puis reporte le résultat `focal_px` dans `[camera]`.

Les paramètres du client LLM sont séparés dans `llm_settings.py` et configurés
par les variables d’environnement `LLM_*`.

### FILE: src/irobot/common/domain/skills/README.md
# Skills du robot

Ce package regroupe les compétences exécutables du robot selon un contrat
commun (`Skill`, `SkillContext`, `SkillResult`).

## Contrat

Chaque skill implémente :
- `execute(context) -> SkillResult`
- optionnellement `validate(context) -> bool`

Les skills n'accèdent pas directement aux GPIO ; elles passent par
`RobotController` injecté dans le contexte.

## Organisation

### Primitives
- `MoveForwardSkill`
- `MoveBackwardSkill`
- `TurnLeftSkill`
- `TurnRightSkill`
- `StopMotionSkill`

### Perception
- `DetectObjectSkill`
- `DetectObstacleSkill`

### Behaviors composites
- `ApproachTargetSkill`
- `MoveCircleSkill`

## Note importante sur `MoveCircleSkill`

`MoveCircleSkill` est un behavior composite, pas une primitive.
Il doit être interprété comme une séquence de primitives (rotation + avance)
pilotée par l'orchestrateur.

Exemple logique de plan :

```python
plan = [
  ("turn_left", 0.5),
  ("move_forward", 0.2),
  ("turn_left", 0.5),
  ("move_forward", 0.2),
  ("stop_motion", None),
]
```

## Exemple de résultat

```python
SkillResult(
  status="success",
  message="...",
  data={...},
  confidence=0.9,
  next_action="skill_name",
)
```

### FILE: src/irobot/common/hardware/audio/README.md
# Audio matériel

Ce package fournit les fonctions audio de bas niveau utilisées par le runtime
vocal. Il ne planifie pas les commandes et ne pilote pas le robot.

- `audio_utils.py` détecte les sources disponibles et résout le périphérique
  d'entrée (Bluetooth, WM8960 ou périphérique ALSA par défaut).
- `voice_input.py` capture le son avec `arecord` et le transcrit avec Vosk.

Le runtime vocal (`irobot.interfaces.voice_runtime`) assemble ces composants :
il choisit le périphérique, récupère les transcriptions, puis les transmet à
la logique d'interprétation.

# Caméra et perception

Ce package fournit la perception visuelle du robot à partir de la caméra
Picamera2. Le pipeline live acquiert les images dans un thread dédié, les
oriente, applique le traitement d'image commun, puis ne lance que le détecteur
correspondant à la cible demandée. Il renvoie une `ObjectDetection` ou `None` ;
il ne commande pas les moteurs et n'enregistre pas les images.

## Modules

| Module | Responsabilité |
|---|---|
| `camera_live_perception_pipeline.py` | Pipeline Picamera2, thread de capture, sélection de la cible, amélioration des images et lissage exponentiel des distances. Contient aussi `ExponentialSmoother`. |
| `frame_enhancer.py` | Correction optionnelle du contre-jour (CLAHE sur le canal L en LAB) et configuration de la compensation d'exposition Picamera2. |
| `detector/target_detector.py` | Aiguillage d'une image vers le détecteur de la cible demandée ; charge le détecteur de visages au premier besoin. |
| `detector/color_detector.py` | Détection des balles rouges et jaunes et estimation de leur distance visuelle. |
| `detector/aruco_detector.py` | Détection et estimation de pose d'un marqueur ArUco. |
| `detector/face_detector.py` | Détection YuNet d'un visage, avec mémoire temporaire de la dernière détection. |
| `detector/distance_estimator.py` | Estimation de distance selon le modèle du sténopé. |
| `detector/base_detector.py` | Types et abstractions communs aux détecteurs. |

Le contrat des cibles et des résultats (`PerceptionTarget`,
`TargetFrameDetector`, `ObjectDetection`) est défini dans
[`interfaces/perception_contracts.py`](../../interfaces/perception_contracts.py).

## Utilisation dans le runtime

Le runtime matériel construit `CameraLivePerceptionPipeline` et l'expose sous
le contrat `ObjectPerceptionPipeline`. Un consommateur demande une cible avec
`detect(*, target=...)` :

```python
from irobot.common.hardware.camera.camera_live_perception_pipeline import CameraLivePerceptionPipeline
from irobot.common.domain.perception import PerceptionTarget

camera = CameraLivePerceptionPipeline()
try:
    detection = camera.detect(target=PerceptionTarget.YELLOW_BALL)
finally:
    camera.close()
```

Les cibles sont `RED_BALL`, `YELLOW_BALL`, `ANY_BALL`, `USER_MARKER` et `FACE`.
Les alias textuels sont convertis par `PerceptionTarget.from_value` : `ball`/`balle`
vers les balles, `marker`/`tag` vers ArUco, `face`/`human`/`moi`/`personne`/`humain`/`visage`
vers le visage. Le résultat contient notamment la position
(`left`, `center`, `right` ou `UNKNOWN`), la confiance, la boîte éventuelle et
les distances en centimètres. Une absence de cible dans l'image retourne `None`.

Le pipeline utilise par défaut la caméra 0 et démarre la capture à sa
construction. `autostart=False` permet de créer l'objet sans démarrer le thread,
notamment pour les tests. `close()` demande l'arrêt et attend le thread ; si un
délai explicite expire avant son arrêt, une `TimeoutError` est levée. Picamera2
peut être absent sur les plateformes sans Raspberry Pi : dans ce cas, le
pipeline journalise l'indisponibilité et termine son thread. L'injection d'un
`TargetFrameDetector` permet de tester le pipeline sans utiliser les détecteurs
par défaut.

## Réglages et limites

Les paramètres caméra sont lus depuis la configuration du runtime, section
`[camera]` de `runtime_settings.toml` :

- `capture_size_px` configure la capture ; l'image est tournée de 90° dans le
  sens horaire avant détection.
- `exposure_value` règle la compensation d'exposition si le contrôle
  Picamera2 `ExposureValue` est disponible.
- `clahe_enabled` et `clahe_clip_limit` activent et règlent la correction locale
  du contraste.
- `ball_diameter_cm` et `focal_px` configurent les estimations visuelles.
- L'identité du marqueur, les paramètres de YuNet et la taille de l'image
  orientée règlent leurs détecteurs respectifs.

La distance d'une balle est estimée à partir de son diamètre apparent et de son
diamètre réel configuré. Celle d'un visage est indicative et dépend de la
largeur réelle du visage. La distance d'un marqueur est obtenue par pose et
dépend de la taille physique connue du marqueur et de la calibration caméra.
Ces estimations ne sont pas des mesures de sécurité : elles doivent être
calibrées et vérifiées sur le robot. Le capteur ultrason reste distinct et
n'est pas fusionné avec la distance de la cible visuelle.

Le pipeline applique un filtre exponentiel aux distances. Son coefficient
`smoothing_alpha` est compris dans `]0, 1]` et vaut `0.4` par défaut. Le filtre
est réinitialisé lorsqu'une cible change ou qu'une détection est perdue.

Pour le modèle YuNet et les détails de réglage, consulter le
[guide du package](../../README.md#détection-de-visages) et la documentation
du [diagnostic vision](../../README.md#diagnostic-vision).

# Capteur HC-SR04

`hc_sr04.py` fournit le pilote GPIO du capteur ultrasonique HC-SR04. Il mesure
la distance du premier obstacle en chronométrant le retour de l'impulsion
ultrasonore. Les broches sont configurées en numérotation BCM : TRIG sur GPIO 17
et ECHO sur GPIO 27 par défaut.

La classe `HC_SR04` expose `read_distance_cm()`, qui renvoie la distance en
centimètres, `math.inf` si rien n'est détecté dans la portée configurée (400 cm
par défaut), ou `None` si le capteur ne répond pas. Les lectures sont sérialisées et une mesure
valide est réutilisée pendant 50 ms. Appelez `cleanup()` pour libérer les GPIO ;
le contexte d'utilisation via `try/finally` garantit leur fermeture.

## Broches GPIO utilisées

Le capteur utilise les broches BCM (Broadcom) du Raspberry Pi :

- TRIG → GPIO 17 (sortie, déclenche l'émission ultrasonore)
- ECHO → GPIO 27 (entrée, reçoit le signal de retour)

Les broches peuvent être modifiées avec `--trigger-pin` et `--echo-pin`.
Connectez également le GND du capteur au GND du Raspberry Pi.

## Test en ligne de commande

Sur le Raspberry Pi, avec `gpiozero` installé :

```bash
uv run hc-sr04 [--once] [--trigger-pin GPIO] [--echo-pin GPIO] \
    [--interval SECONDES] [--max-distance CM]
```

Sans `--once`, les mesures se répètent toutes les 0,5 seconde. `Ctrl+C` arrête
le test proprement.

> **Attention :** l'entrée GPIO du Raspberry Pi tolère 3,3 V au maximum. Le
> signal ECHO d'un HC-SR04 classique peut être à 5 V : utilisez un diviseur de
> tension ou un convertisseur de niveau avant de le relier au GPIO 27.

# Smart Car 2WD (L298N)

Ce module fournit le pilote matériel d'une voiture 2 roues motrices (2WD) depuis
un Raspberry Pi via un pont en H L298N. Les moteurs sont commandés par les sorties
IN1–IN4 ; ENA et ENB reçoivent un signal PWM commun pour régler leur vitesse.
La logique de commande et la surveillance du HC-SR04 sont portées par
`RobotController` ; le CLI est dans `cli.py`.

Les commandes sont fournies par le point d'entrée `smart-car` :

```text
uv run smart-car {forward,backward,left,right,stop} [options]
```

## Options

| Option | Défaut | Description |
|---|---|---|
| `command` | – | `forward`, `backward`, `left`, `right` ou `stop` |
| `--speed` | `1.0` | Vitesse de `0.0` (arrêt) à `1.0` (maximum), appliquée aux deux moteurs |
| `--duration` | `-1` | Durée en secondes ; `-1` = indéfini (Ctrl+C), `0` = arrêt immédiat |
| `--obstacle-threshold-cm` | `20.0` | Arrête la voiture si le HC-SR04 mesure un objet à moins de X cm |
| `--obstacle-check-interval` | `0.2` | Intervalle (s) entre deux vérifications du capteur pendant un déplacement |

## Broches GPIO utilisées

Le script utilise les broches BCM (Broadcom) du Raspberry Pi :

- IN1 → GPIO 5
- IN2 → GPIO 6
- IN3 → GPIO 16
- IN4 → GPIO 24
- ENA → GPIO 12
- ENB → GPIO 13

Les broches sont numérotées en mode BCM, pas selon leur numéro physique sur le
connecteur 40 broches. Le GND du Raspberry Pi, du L298N et de l'alimentation
moteur doit être commun. La batterie moteur alimente le L298N, jamais les GPIO
du Raspberry Pi.

## Exemple de câblage

```text
Raspberry Pi            L298N / moteur
--------------------------------------
GPIO 5  -> IN1
GPIO 6  -> IN2
GPIO 16 -> IN3
GPIO 24 -> IN4
GPIO 12 -> ENA
GPIO 13 -> ENB
GND     -> GND du module

Batterie moteur + -> alimentation du module
Batterie moteur - -> GND du module
```

Le HC-SR04 utilise aussi les broches BCM suivantes :

```text
Raspberry Pi            HC-SR04
--------------------------------
GPIO 17 -> TRIG
GPIO 27 <- ECHO
5V      -> VCC
GND     -> GND
```

**Protection indispensable :** le signal ECHO d'un HC-SR04 classique peut
atteindre 5 V, alors que les GPIO du Raspberry Pi tolèrent au maximum 3,3 V.
Intercalez un diviseur de tension ou un convertisseur de niveau entre ECHO et
GPIO 27.

## Commandes disponibles

```bash
uv run smart-car forward
uv run smart-car backward
uv run smart-car left
uv run smart-car right
uv run smart-car stop
```

## Contrôle de vitesse

Le paramètre `--speed` doit être compris entre `0.0` et `1.0` :
- `0.0` = moteurs à l'arrêt
- `1.0` = vitesse maximale
La même valeur est appliquée aux deux moteurs.

Exemples :

```bash
uv run smart-car forward --speed 0.5
uv run smart-car left --speed 0.3
uv run smart-car right --speed 1.0
```

## Durée d'exécution

Le paramètre `--duration` permet de limiter le temps d'action :
- `--duration 2` : avance pendant 2 secondes puis stop
- `--duration 0` : arrêt immédiat
- sans `--duration` : mouvement continu jusqu'à Ctrl+C

Exemples :

```bash
uv run smart-car forward --speed 0.7 --duration 2
uv run smart-car backward --speed 0.6
uv run smart-car stop
```

## Détection d'obstacle

Pendant `forward`, `left` ou `right`, le HC-SR04 (TRIG GPIO 17, ECHO GPIO 27)
est vérifié à chaque intervalle configuré :
- distance strictement inférieure à `--obstacle-threshold-cm` : arrêt des moteurs
  et fin de la commande ;
- mesure absente : jusqu'à cinq lectures sont tentées ; si aucune n'est valide,
  le système s'arrête par sécurité ;
- `backward` ignore ce capteur orienté vers l'avant ; `stop` ne lance pas de
  vérification.

Le seuil par défaut est de 20 cm. Si le HC-SR04 n'est pas branché correctement,
les déplacements surveillés peuvent donc s'arrêter après des mesures invalides.

```bash
uv run smart-car forward --speed 0.5 --obstacle-threshold-cm 15
uv run smart-car forward --duration 5 --obstacle-check-interval 0.1
```

## Exemple complet

```bash
uv run smart-car forward --speed 0.8 --duration 3
uv run smart-car right --speed 0.4 --duration 1.5
uv run smart-car stop
```

## Sécurité

- Ne branche pas directement la batterie moteur sur les GPIO du Raspberry Pi.
- Ne relie pas directement la sortie ECHO 5 V du HC-SR04 à un GPIO du Pi :
  utilise un diviseur de tension ou un convertisseur de niveau.
- Vérifie que le GND du Pi et le GND du module moteur sont reliés.
- Vérifie également que le HC-SR04 et le Raspberry Pi partagent le GND.
- Utilise une alimentation adaptée aux moteurs.
- Déconnecte la batterie avant de modifier les câbles.

## Dépannage

### La voiture ne bouge pas

Vérifie :
- alimentation moteur présente
- GND Pi connecté au GND du L298N
- broches GPIO correctes
- ENA / ENB correctement câblés
- tu n'utilises pas les mauvais numéros BCM

### Une roue tourne seule

Cela indique généralement un problème de masse commune ou un câblage incohérent.

Vérifie :
- le GND du Pi est bien relié au GND du module L298N
- la batterie moteur est bien branchée au module, pas sur le Pi
- les sorties moteur ne sont pas en court-circuit

### Le script ne démarre pas

Vérifie que `gpiozero` est bien installé :

```bash
python3 -c "import gpiozero; print(gpiozero.__version__)"
```

Et si besoin :

```bash
uv sync --project .
```

## Notes de conception

Le moteur est contrôlé avec :
- des sorties logiques `DigitalOutputDevice` pour la direction
- des sorties PWM `PWMOutputDevice` pour la vitesse sur ENA / ENB

La logique interne est simple :
- direction = commande logique IN1/IN2 / IN3/IN4
- vitesse = niveau PWM sur ENA / ENB

Le script est prévu pour des tests de moteur et des démonstrations de pilotage simple sur Raspberry Pi.
